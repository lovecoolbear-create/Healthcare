## 1. 设计核心理念 (Design Philosophy)

本项目遵循 **"双端分离，逻辑统一"** 的设计原则，旨在为不同角色的用户提供最匹配其工作流的交互体验。

### 1.1 角色与场景
*   **客户端 (Client)**: 极简、温暖、低负担。
    *   **关键词**: 信任 (Trust)、陪伴 (Companion)、养成 (Habit)。
    *   **主色调**: Emerald Green (#10b981) - 象征健康、生命力。
    *   **核心交互**: 大按钮打卡、滑动条反馈、一键补货 (One-Click Refill)。
    *   **库存预警**: 首页置顶 Banner 提示“库存不足 X 天”，点击直达库存页。
*   **营养师端 (Nutritionist/Admin)**: 专业、高效、全局掌控。
    *   **关键词**: 数据 (Data)、洞察 (Insight)、行动 (Action)。
    *   **主色调**: Indigo Blue (#4f46e5) / Slate (#0f172a) - 象征专业、冷静、商务。
    *   **核心交互**: CRM 卡片式看板、右侧抽屉详情、高密度数据表格。
    *   **发货交互**: 订单管理抽屉支持“一键发货”与物流填单。

### 1.2 Web 数据中心 (Web Data Center)
Web 端被定义为 **"总店深度监控室"**，不仅仅是管理后台，更是数据分析与决策中心。
*   **CRM 化设计**: 摒弃传统的 CRUD 表格，采用 "指标卡片 + 优先级列表" 的 CRM 仪表盘设计。
*   **响应式适配**:
    *   **Desktop**: 完整的三栏/两栏布局，利用宽屏展示更多数据维度。
    *   **Mobile (H5)**: 强制锁定桌面视图，不启用移动端布局。

## 2. UI 设计规范 (UI Design System)

### 2.1 色彩系统 (Color Palette)
*   **Brand Primary (Client)**: `bg-emerald-500` (Main), `bg-emerald-50` (Light/Background)
*   **Brand Primary (Admin)**: `bg-indigo-600` (Main), `bg-indigo-50` (Light/Background)
*   **Neutral**: `bg-slate-50` (Page Bg), `bg-white` (Card Bg), `text-slate-900` (Heading), `text-slate-500` (Body)
*   **Semantic**:
    *   **Success**: `text-emerald-500` (正常/运行中/订单完成)
    *   **Warning**: `text-amber-500` (观察/中风险/已发货)
    *   **Danger**: `text-rose-500` (预警/高风险/库存不足/待发货)

### 2.2 组件模式 (Component Patterns)

#### A. 核心指标卡片 (Metrics Card)
用于 Dashboard 及各模块首页，展示关键业务指标。
*   **结构**: 图标 (左上) + 标题 (右上) + 核心数值 (中) + 趋势/状态标签 (下)。
*   **样式**: 圆角 `rounded-3xl`，白色背景，轻微阴影 `shadow-sm`，Hover 时上浮 `hover:-translate-y-1`。

#### B. 优先级行动列表 (Priority Action List)
用于替代传统分页表格，聚焦"当前需要处理的事项"。
*   **结构**: 
    *   **高风险区**: 红色/橙色背景高亮，置顶展示。
    *   **普通区**: 标准列表。
*   **交互**: 点击行弹出右侧抽屉 (Drawer) 查看详情，而非跳转新页面。

#### C. 右侧抽屉 (Right Drawer)
用于展示详情、编辑表单，保持上下文不中断。
*   **宽度**: `w-96` (小) 或 `w-[600px]` (大)。
*   **动画**: `slide-in-from-right`。

#### D. 移动端/桌面端分流 (Responsive Split)
*   **实现方式**: 使用 `v-if="isDesktop"` 结合 Uni-app 的条件编译 `<!-- #ifdef H5 -->`。
*   **策略**:
    *   **H5 Web 端**: 强制 `isDesktop = true`，禁用移动端布局。
    *   **小程序端**: 使用原生 `pages.json` TabBar 导航。

## 3. 模块设计详情 (Module Specifications)

### 3.1 工作台 (Dashboard)
*   **Desktop**: 
    *   顶部: 4 个核心指标卡 (总客户、今日打卡、异常预警、待处理发货)。
    *   左侧: 高风险客户列表 (WROM < 60)。
    *   右侧: 快捷操作入口 (新增客户、发货)。

### 3.2 客户档案库 (Clients)
*   **Desktop**: 
    *   CRM 风格表格：包含头像、姓名、WROM 评分 (颜色编码)、最后打卡时间、库存状态。
    *   详情抽屉：包含个人信息、当前方案、最近 7 天打卡热力图、库存与订单记录。
    *   双评分总览：提供 WROM / RPS 切换 Tab，并在名称旁提供 `?` 公式说明入口。
*   **Client Inventory (小程序客户端)**:
    *   **库存预警计算口径**: 基于**方案内所有产品**（`ownProtocol.items`）计算，而非仅已有库存的产品。
    *   **低库存判定规则**: 
        *   有库存但覆盖天数 `< 7天` → 红色预警
        *   无库存记录（方案中有但库存中缺失）→ 视为库存=0，红色预警显示"未入库"
    *   **预警状态流转**:
        | 状态 | 颜色 | 触发条件 | 操作按钮 |
        |------|------|----------|----------|
        | **库存预警** | 🔴 红色 | 需补货且无进行中的订单 | "一键补货" |
        | **补货中** | 🟡 黄色 | 有等待发货的订单 | 无操作，提示"等待顾问发货" |
        | **已发货** | 🟢 绿色 | 有已发货订单 | "确认收货" |
    *   **订单匹配逻辑**: 虚拟库存项（未入库产品）通过 `product_name` 匹配订单中的 `name` 字段。
    *   **计划外库存展示**: 显示“未纳入计划”提示，不参与低库存预警与补货入口。
    *   **可用天数计算**: 仅对健康计划内产品计算并展示；无计划产品不计算可用天数。

### 3.3 系统支撑 (System Support)
*   **干预触发器 (Triggers)**: 
    *   卡片式网格布局。
    *   可视化参数配置 (Switch 开关 + Input 阈值)。
*   **数据分析报告 (Reports)**: 
    *   可视化图表：WROM 趋势柱状图、健康风险分布环形图。
    *   CSS 纯代码绘图，避免引入重型图表库。
*   **知识库 (Knowledge)**: 
    *   左侧导航/顶部 Tab 分类 (产品/文献/话术)。
    *   模态框 (Modal) 编辑内容。

### 3.4 WROM 解读口径（v1.3）
*   **定位**: WROM 用于“健康执行风险分层 + 跟进优先级排序”，不等于消息活跃度排行榜。
*   **库存分展示原则**:
    *   采用“覆盖天数”作为解释口径，并提示分段含义：`<7天` 缺货风险、`7-45天` 健康区、`>45天` 可能囤货。
    *   当客户“有任务但 7 天内 0 完成且覆盖天数过高”时，前端需可识别为囤货风险场景，不展示为高健康库存状态。
*   **互动分展示原则**:
    *   互动维度解释为“健康行为参与度”，核心依据是任务/饮水/体感记录，而非纯聊天条数。
    *   对低互动偏好客户采用非惩罚策略，不因少聊天而显著拉低整体风险评分。
*   **运营提示**: 报表与看板中的互动信息可保留“通知已读/留言次数”作为辅助指标，但不应作为核心扣分依据。

### 3.5 RPS 解读口径（v1.5）
*   **定位**: RPS 用于评估客户“商业价值稳定性”与“复购倾向”，而非单纯的满意度调研。
*   **指标移除**: 已移除“价格敏感度”指标。理由：营养顾问无法直接控制产品定价，且健康计划中“效果”才是核心复购驱动力。
*   **预警机制**: 
    *   **ΔRPS < 0**: 视为“关键负面预警”，状态标记为 **“待回复”**。
    *   **人机结合**: 严禁使用全自动回复，要求顾问根据 RPS 各维度的具体短板（如物流时延、体感下降）进行个性化沟通。
*   **UI 优化**: 
    *   客户详情页已清理冗余信息块，将执行摘要与各维度明细合并。
    *   指标名称旁增加 `?` 图标，点击可展示公式说明详情。

### 3.6 运营闭环交互（v1.4）
*   **首要行动执行**:
    *   在 RPS 首要行动卡中提供“标记已执行”按钮，一键记录行动执行。
*   **复核回显**:
    *   展示“行动复核记录”列表，包含状态（待复核/已复核）与 `ΔWROM / ΔRPS`。
    *   待复核项显示预计复核日期，已复核项显示变化结果，支持顾问快速判断动作有效性。
*   **工作台联动**:
    *   当复核后 `ΔRPS < 0` 时，客户自动进入 RPS 风险待办，并在卡片文案中标注“复核后下滑”。

## 4. 交互与动效 (Interaction & Motion)
*   **Hover**: 所有可点击卡片/按钮均有 Hover 态 (颜色加深或阴影加重)。
*   **Transition**: `transition-all duration-300`，确保状态切换平滑。
*   **Feedback**: 操作成功/失败必须有 Toast 提示；危险操作 (如退出登录、删除) 必须有二次确认 Modal。

## 5. 面向个人顾问的上线验收标准 (Go-Live Readiness for Solo Nutritionist)

### 5.1 验收目标
在不追求功能完备的前提下，确保系统达到“可控可用、可持续服务”的最低商用标准，可支持个人营养顾问开展日常客户管理。

### 5.2 上线判定规则
*   **总则**: 10 条验收项中至少通过 8 条。
*   **强制条件**: P0 项必须全部通过 (5/5)。
*   **建议条件**: P1 项至少通过 3 条 (3/5)。

### 5.3 P0 必过项 (Blocking Criteria)
1.  **登录可用**: 顾问端与客户端连续 3 次登录成功，无阻断性报错。
2.  **核心链路闭环**: 方案下发、打卡回传、补货申请均满足“提交 -> 落库 -> 对端可见”。
3.  **数据隔离正确**: 客户数据不串号，不出现跨客户污染。
4.  **异常可恢复**: 请求失败有明确提示且支持用户重试，不出现卡死状态。
5.  **资源应急可执行**: 当云资源异常或超限时，具备明确降级与恢复流程。

### 5.4 P1 建议项 (Quality Criteria)
1.  **跨端一致性**: 同一业务数据在 Web 与小程序展示一致。
2.  **同步时效**: 关键操作 5 秒内有前端反馈，30 秒内可在对端看到结果。
3.  **可运维性**: 问题可快速定位到集合、云函数或页面模块。
4.  **可教学性**: 新顾问可在 30 分钟内完成首次完整业务流程。
5.  **可收费性**: 可明确量化“节省时间、提升留存、提高复购”价值点。
6.  **库存口径一致性**: 顾问端“库存告急”与客户端“低库存”必须基于同一规则（计划内 + 阈值判定）。

### 5.5 评分方法
*   **单项评分**: 2 分 = 完全满足；1 分 = 部分满足；0 分 = 不满足或无证据。
*   **证据要求**: 每项至少提供操作截图、数据库查询结果或跨端一致性证明中的一种。
*   **上线建议**:
    *   90-100 分: 可正式试运营。
    *   80-89 分: 可小范围试运营。
    *   70-79 分: 仅建议内部演示。
    *   <70 分: 不建议对外试用。

### 3.7 配方管理标准流程（Protocol Management Standard Process）v1.5

#### 3.7.1 设计目标
建立标准化的配方全生命周期管理流程，实现：
1. **配方效果可追踪**：每个配方的使用周期、客户反馈、WROM变化可量化分析
2. **客户告知自动化**：配方切换时间自动通知客户，避免人工遗漏
3. **配方库沉淀**：标准化配方可复用，形成机构知识资产

#### 3.7.2 核心概念
| 概念 | 说明 | 状态流转 |
|------|------|----------|
| **配方模板 (Template)** | 标准化配方原型，可被多个客户复用 | draft → active → deprecated |
| **客户方案 (Protocol)** | 基于模板或自定义为客户制定的具体方案 | pending → active → completed → expired |
| **主方案 (Primary Protocol)** | 客户的第一个/主要方案，具有编辑、同步、停止权限 | active |
| **附加方案 (Secondary Protocol)** | 客户后续添加的并行方案，与主方案共存 | active |
| **方案周期 (Protocol Cycle)** | 方案从开始日期到结束日期的完整使用周期 | - |
| **方案切换 (Protocol Switch)** | 旧方案结束/新方案开始的自动/手动过渡过程 | - |
| **多方案并行 (Multi-Protocol)** | 同一客户同时执行多个方案（如减脂+睡眠） | active + active |

#### 3.7.3 配方生效时间机制

**A. 时间设置**
- **开始日期 (start_date)**: 方案生效日期，可设置为未来日期
- **结束日期 (end_date)**: 方案失效日期，可选，到期自动停用
- **立即生效**: start_date = 当前日期，保存后立即同步到客户今日计划
- **预约生效**: start_date > 当前日期，保存后状态为 pending，到期自动激活

**B. 状态流转规则**

**单方案模式（替换逻辑）**
```
保存新方案
├── start_date = 今天
│   └── 状态: active → 立即替换旧方案 → 同步今日计划
│
└── start_date > 今天
    └── 状态: pending → 保留旧方案 → 客户看到"新方案即将生效"提示
        └── 到达 start_date
            └── 自动激活 → 旧方案标记 completed → 新方案同步今日计划
```

**多方案模式（并行逻辑）**
```
添加新方案（已有主方案）
├── 保存为附加方案
│   ├── plan_index = 1（第二个方案）
│   ├── is_secondary = true
│   └── 状态: active → 与主方案并行
│
└── 客户打卡任务包含
    ├── 主方案任务
    └── 附加方案任务（按 plan_index 排序）
```

**方案优先级规则**
- 主方案（plan_index = 0, is_secondary = false）：可编辑、可同步、可停止
- 附加方案（plan_index ≥ 1, is_secondary = true）：仅可查看、不可编辑
- 所有并行方案的任务合并到客户今日打卡列表

**C. 自动切换逻辑**
- 每日首次获取今日计划时，检查 pending 方案是否到期
- 到期方案自动激活，旧方案自动停用（soft delete，保留历史）
- 新方案任务自动同步到客户今日计划板块
- 向客户发送方案切换通知（小程序消息/服务通知）

#### 3.7.4 配方效果追踪（Protocol Effectiveness Tracking）

**A. 设计理念**
配方效果追踪不作为独立报表存在，而是**叠加在健康数据曲线上**。这样顾问和客户可以在查看WROM、体感评分、健康指标等趋势时，直观地看到：
- 这段上升曲线对应的是哪个健康计划
- 下降阶段是否因为客户没有执行健康计划
- 不同配方切换时数据的变化趋势

**B. 图表上的配方阶段标记**
在健康趋势图表（体重、体脂、WROM、体感评分等）上，用以下方式标记配方阶段：

```
图表示例：WROM 趋势（30天视图）

100 |                                          ╱
    |            [免疫增强方案]                ╱
 80 |    ●─────●────────────●────────────────●
    |   /      |           |               /
 60 |  /       |  ●──●──●  |    ●──●──●  /
    | /        | /       \ |   /       \ /
 40 |/         |/         \|  /         ●
    |          |           | /
 20 |          |           |/
    └──────────┼───────────┼──────────────
              1/15      2/1         2/15
            [开始]    [基础调理]    [结束]
```

**标记元素**：
- **背景色带**：每个配方阶段用不同颜色的半透明背景色带区分
- **垂直边界线**：配方开始/结束日期用虚线标记
- **顶部标签**：**完整显示配方名称**（顾问定制配方，无隐私问题）
- **图例**：图表下方显示配方颜色图例和日期范围
- **交互**：点击配方色带区域弹出该阶段详情（依从率、体感评分、WROM变化）

**C. 适用图表类型**
| 图表 | 客户端 | 顾问端 | 配方标记说明 |
|------|--------|--------|--------------|
| WROM 趋势 | ✓ | ✓ | 显示配方对整体健康评分的影响 |
| 体感评分趋势 | ✓ | ✓ | 显示配方对主观感受的改善 |
| 体重/体脂曲线 | ✓ | ✓ | 显示配方对体成分的影响 |
| 饮水记录 | ✓ | - | 辅助参考，不强调配方关联 |
| 血糖/血脂指标 | ✓ | ✓ | 显示配方对特定指标的改善 |

**D. 无配方阶段的显示**
- **无需特别标注** - 无背景色带的区域即表示该期间未制定健康计划
- 留白本身就是一种视觉暗示，提示顾问该阶段需要关注或补充配方

#### 3.7.5 客户告知机制

**A. 方案预约通知**
- 新方案保存后，客户立即收到「新方案已预约」通知
- 显示：方案名称、生效日期、倒计时天数
- 位置：小程序首页置顶提醒卡片（橙色高亮）

**B. 方案切换通知**
- 方案生效当日，客户收到「今日开始使用新方案」通知
- 显示：新方案详情、今日任务预览
- 位置：小程序今日计划板块 + 服务消息推送

**C. 方案即将结束通知**
- 方案到期前3天，提醒客户和顾问
- 提示：是否需要续订/调整方案
- 位置：顾问端客户列表标记 + 客户端提醒

#### 3.7.6 交互设计规范

**A. 顾问端 - 方案制定页**
```
┌─────────────────────────────────────────┐
│  📋 制定健康方案 - 客户: 张三              │
├─────────────────────────────────────────┤
```

#### 3.7.8 标准操作流程（SOP）

**场景1: 新客户首次制定方案**
1. 顾问评估客户健康状况
2. 选择现有模板或自定义配方
3. 设置立即生效（start_date = 今天）
4. 保存后客户立即在小程序看到今日任务

**场景2: 老客户方案续订/调整**
1. 查看当前方案效果报告
2. 基于数据调整配方（增减产品、调整用量）
3. 可设置预约生效（如给客户囤货消耗时间）
4. 保存后客户看到「新方案即将生效」提示

**场景3: 预约方案到期自动切换**
1. 系统每日检查 pending 方案
2. 到期方案自动激活
3. 旧方案标记为 completed
4. 新方案任务同步到客户今日计划
5. 向客户发送推送通知

**场景4: 添加并行方案（多方案管理）**
1. 客户已有主方案执行中（如：改善睡眠）
2. 顾问评估客户新增健康目标（如：降血脂）
3. 顾问点击「从配方库选择」→ 选择「降血脂」配方
4. 系统保存为附加方案：
   - plan_index = 1（第二个方案）
   - is_secondary = true
   - 状态：active，与主方案并行
5. 客户小程序显示：
   - 今日打卡包含两个方案的所有产品
   - 按方案分组显示（改善睡眠 + 降血脂）
6. 顾问端显示：
   - 主方案：显示编辑/同步/停止按钮
   - 附加方案：仅显示详情，不可编辑

## 6. 技术架构约束与已知问题 (Technical Constraints & Known Issues)

### 6.1 CLI 项目 H5 模式 uniCloud 调用限制

#### 6.1.1 问题描述

项目在 **2026-05-28** 升级到 Healthcare 2.0 时，从 **HBuilderX 原生项目** 被替换为 **uni-app CLI 项目**（使用 `uni-preset-vue` Vite 模板）。这导致通过「HBuilderX 运行菜单 → 运行到浏览器」时，`uniCloud.callFunction()` 报错：

```
SYS_ERR: uni-app cli项目内使用uniCloud需要使用HBuilderX的运行菜单运行项目，
且需要在uniCloud目录关联服务空间
```

#### 6.1.2 根因分析

| 对比项 | HBuilderX 原生项目 | CLI 项目（当前） |
|--------|-------------------|-----------------|
| 创建方式 | HBuilderX 新建向导 | `npx degit dcloudio/uni-preset-vue#vite` |
| `package.json` name | 任意名称 | `uni-preset-vue` |
| 构建工具 | HBuilderX 内部管理 | 自有 `vite.config.ts` |
| 父目录 `about/package.json` | 有 → 被识别为内部项目 | 无 → 被识别为 CLI 项目 |
| **H5 模式 uniCloud 注入** | 自动注入 `UNI_CLOUD_PROVIDER` | **不注入** → SDK 报错 |

HBuilderX 通过检查项目父目录是否存在 `about/package.json`（name === 'about'）来区分项目类型。CLI 项目的父目录没有此文件，因此：

1. `@dcloudio/vite-plugin-uni` 的 `initDefine()` 将 `process.env.UNI_CLOUD_PROVIDER` 设为空字符串
2. Vite 编译时将 SDK 中的该变量替换为 `"[]"`（空数组）
3. `uni-cloud.es.js` 运行时检测到配置数组长度 ≠ 1，拒绝初始化
4. 所有云函数调用被替换为抛出错误函数

**注意：小程序端不受影响**，因为小程序编译走的是独立的编译流程（直接读取 `manifest.json` 中的 uniCloud 配置），不依赖此环境变量注入。

#### 6.1.3 解决方案：HTTP Gateway 云函数

采用 **HTTP URL 化网关方案**，彻底绕过 CLI 项目的 SDK 注入限制。

**架构：**
```
H5 浏览器 ──fetch(POST)──→ [http-gateway 云函数] ──uniCloud.callFunction()──→ 实际云函数
                              ↑
                        服务端执行，SDK 正常工作（读取 manifest.json 配置）
小程序端 ──uniCloud.callFunction()──→ 直接调用（无变化）
```

**涉及文件：**

| 文件 | 说明 |
|------|------|
| `uniCloud-alipay/cloudfunctions/http-gateway/index.js` | 网关云函数：接收 HTTP POST，在服务端转发 `uniCloud.callFunction()` |
| `src/utils/cloud.ts` | 统一调用入口：H5 用 HTTP fetch 调网关，小程序用 SDK 直接调 |

**部署要求（一次性操作）：**

1. 在 HBuilderX 中右键 `http-gateway` → 「上传部署」
2. 在 uniCloud 控制台 → 云函数 → http-gateway 详情 → 「设置URL的PATH部分」→ 输入 `/http-gateway`
3. 记录默认域名并更新 `cloud.ts` 中的 `GATEWAY_URL` 常量

当前已配置的默认域名：
```
https://env-00jy5xpjho0v.dev-hz.cloudbasefunction.cn/http-gateway
```

#### 6.1.4 注意事项

- **不可回退为原生项目**：回退会丢失 Vite、TypeScript、Tailwind CSS 等工程化能力
- **新增云函数无需额外配置**：所有云函数都通过同一个 http-gateway 入口转发，只需在请求中指定 `name` 字段即可
- **跨域已处理**：网关云函数返回头包含 `Access-Control-Allow-Origin: *`
- **安全建议**：生产环境应绑定自定义域名 + 添加鉴权机制（如 token 校验），避免暴露内部 API

### 6.2 代码修改安全规范（强制遵守）

> 本节记录项目历史中因修改引入回归 bug 的教训，**后续所有代码变更必须遵守**。

#### 6.2.1 禁止在 H5 代码中使用 require()

| 项目 | 说明 |
|------|------|
| **问题日期** | 2026-06-22 |
| **问题描述** | 将 `cloud.ts` 中硬编码的 GATEWAY_URL 改为 `require('./config/development.js')` 动态加载后，H5 浏览器模式报错「网关未配置」 |
| **根因** | Vite H5 构建环境是纯 ESM（ES Module），不支持 CommonJS 的 `require()`。运行时 `require is not defined` |
| **修复方式** | 使用内联默认值作为兜底 + 动态 `import()` 作为可选覆盖 |

**强制规则：**

```
❌ 禁止：const config = require('./xxx.js')
✅ 允许：const config = await import('./xxx.js')   // 动态 import
✅ 允许：import config from './xxx.js'              // 静态 import（顶层）
✅ 允许：内联默认值 + import() 可选覆盖            // 最安全（当前采用）
```

#### 6.2.2 变更原则：先保证可用性，再优化

| 原则 | 说明 |
|------|------|
| **最小改动** | 每次修改只解决一个问题，不顺便重构无关代码 |
| **保留兜底** | 移除硬编码值前，必须确保替代方案在所有构建环境（H5/小程序/生产）下都能工作 |
| **改完自测** | 涉及核心路径（如 cloud.ts、main.ts）的修改，必须确认 H5 和小程序两种模式都能正常运行 |
| **不破坏已有功能** | 「优化」不能以牺牲「能用」为代价 |

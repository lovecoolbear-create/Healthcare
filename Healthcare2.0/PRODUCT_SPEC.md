# HealthCare Pro 产品与技术核心规范 (PRODUCT_SPEC) - v6.5 [Consolidated Single Source]

*版本：v6.5 (Consolidated Single Source)*
*日期：2026-03-25*

## 1. 项目定位与核心愿景
*   **定位**：基于 S2B2C 模式的垂直领域 CRM + 健康管理 SaaS 系统。
*   **核心价值**：
    *   **万能模具 (Uni-app)**：一次开发，覆盖小程序双模式（客户/营养师）与 Web 管理端。
    *   **中央大账本 (PostgreSQL/MongoDB)**：基于角色与租户的数据分发，确保数据安全与业务闭环。
    *   **施工图纸保险柜 (Gitee)**：国产化代码托管，保障商业逻辑资产。

## 2. 架构定义 (Architecture)
本项目采用 **Uni-app + 阿里云 UniCloud** 的全端架构。

### 2.1 组成部分
1.  **Gitee (代码仓库)**:
    *   角色：**施工图纸保险柜**。
    *   任务：存储所有界面逻辑。
2.  **阿里云 UniCloud (Serverless)**:
    *   角色：**中央大账本**。
    *   **云数据库 (JQL)**: 原生集成，开箱即用，无需维护服务器。
    *   **云函数**: 处理业务逻辑，连接微信接口。
3.  **Uni-app (开发框架)**:
    *   角色：**万能模具**。
    *   任务：一次开发，分发出 **小程序 (双模式)** 和 **Web 管理后台**。
4.  **小程序端 (Client/Admin Mobile)**:
    *   角色：**全能手机移动店**。
    *   **客户模式 (90% 完成)**: 极简打卡、传体感、看方案、一键补货。
        *   **主要特性**: 深度适配微信小程序环境 (View/Text 标签替换)，解决 SVG 渲染与白屏问题。
    *   **营养师模式**: 手机接收预警、快速批改、即时回复、库存预警处理。
5.  **Web 端 (Web Data Center)**:
    *   角色：**总店深度监控室**。
    *   任务：仅限营养师使用，用于大屏深度复盘、批量导出数据、复杂配方建模、**商品主数据管理**。
    *   **UI/UX 规范**: 详见 `PDR.md`。采用 **CRM 化仪表盘设计**，包含指标卡片、优先级列表、右侧抽屉详情等。
    *   **系统支撑模块**: 包含干预触发器配置、数据分析报告、营养学知识库。

### 2.2 数据结构关键定义 (Data Structure)
*   **商品主数据 (Product Master Data)**:
    *   **管理端 (Web)**: 负责商品的 CRUD（增删改查）。
    *   **移动端 (Mobile)**: 仅读取商品信息。
    *   **唯一标识**: 使用 `product_id` 作为唯一识别码。产品名称变更不影响历史数据关联。
    *   **关键字段**: `name`, `unit`, `icon`, `category`, `price`, `capacity` (容量), `sub_unit` (子单位), `daily_usage` (日用量), `stock` (总库存).
*   **订单结构 (Orders Collection)**:
    *   `order_id`: 唯一订单号
    *   `client_id`: 客户 ID
    *   `items`: 数组 `[{ product_id, product_name (snapshot), quantity, spec }]`
    *   `status`: 0:待发货, 1:已发货, 2:已完成, -1:已取消
    *   `tracking_no`: 快递单号
    *   `delivery_photo`: 物流照片 URL
    *   `created_by`: client 或 dietitian

## 3. 核心业务逻辑 (Core Business Logic)

### 3.1 灵魂公式 (WROM 2.0)
复购指数 **R = 依从性(40%) + 库存(30%) + 体感(20%) + 互动(10%)**。

### 3.1.1 双评分定位（WROM + RPS）
*   **WROM（健康）**: 用于评估客户健康执行风险，指导健康干预优先级。
*   **RPS（复购）**: 用于评估客户复购行为风险，指导运营跟进优先级。
*   **界面交互要求**: 在顾问端客户详情中，WROM 与 RPS 名称旁需提供 `?` 说明入口，点击可查看公式与数据来源说明。

#### 0. 评分阈值与行动指令（红绿灯系统）
| 分数段 | 状态 | 颜色 | 含义 | 营养师行动指令 |
| :--- | :--- | :--- | :--- | :--- |
| **< 60** | **高危** | 🔴 红灯 | 体感崩盘风险 | 立即干预，优先电话或深度沟通 |
| **60 - 80** | **预警** | 🟡 黄灯 | 黄金沟通期 | 重点随访，提供针对性建议 |
| **> 80** | **健康** | 🟢 绿灯 | 良性运行 | 保持轻量鼓励，避免过度打扰 |

#### 1. 依从性 (Adherence) [40%]
*   **定义**: 衡量客户是否按时按量服用。
*   **公式**: $Score = (Count_{Actual} / Count_{Expected}) \times 40$
    *   $Count_{Actual}$: 过去 7 天真实打卡频次。
    *   $Count_{Expected}$: 方案设定的应打卡频次。
*   **坚持天数 (Streak)**:
    *   **规则**: 关联“人”，与配方无关。只要用户每天有打卡记录，天数即累加。
    *   **重置**: 用户断签（当天无打卡记录）则重置为 0。
    *   **客户端实现**: 动态计算连续打卡天数，视觉化展示进度条。

#### 2. 库存水位 (Inventory) [30%] - **核心双端联动逻辑**
*   **定义**: 复购行为的物理倒计时。
*   **核心规则**: 
    *   **自动消耗 (Auto-Consumption)**: 
        *   **触发点**: 客户完成“每日健康打卡” (`updateDailyPlanTasks`)。
        *   **逻辑**: 系统通过正则解析任务剂量 (如 "2粒/次")，自动扣减对应 `product_id` 的个人库存 (`he_inventory`)。
        *   **原子操作**: 使用 `db.command.inc` 确保并发安全。
    *   **覆盖天数计算**: 要求营养师在 Web 端做配方时必须有明确的“每日剂量”。
    *   **核心口径（v6.4）**:
        *   对每个库存项计算可覆盖天数：`CoverageDays = stock * capacity / daily_usage`。
        *   以客户“平均覆盖天数”作为库存状态输入，限定在 0-120 天区间。
        *   分段打分：`<7天` 为高风险低分区，`7-45天` 为健康高分区，`>45天` 进入囤货回落区。
        *   防误判保护：若近 7 天有任务但完成数为 0 且覆盖天数 > 45 天，则库存分上限限制为 12 分，避免“囤货不吃”被高分奖励。
    *   **预警**: 剩余量不足 5 天时，Web 端强制红色置顶；**小程序端首页展示“一键补货”按钮**。
    
    *   **双轨制补货系统 (Dual-Track Replenishment System)**:
        *   **Flow A (客户主动)**: 
            1.  **下单**: 客户在“我的药箱”或“产品目录”中发起订购申请。客户可以订购**全库产品**（Web 端产品库 `he_products`），不仅仅局限于当前已有的库存。生成 `he_orders` (status=0)。
            2.  **发货**: 顾问 Web 端点击“确认发货” -> 调用 `shipOrder` -> 更新订单状态 (status=1)。
            3.  **收货**: 客户小程序点击“确认收货” -> 调用 `confirmOrderReceipt` -> **增加个人库 (`he_inventory`)** -> 更新订单状态 (status=2)。
        *   **Flow B (顾问主动)**: 
            1.  **发货**: 顾问根据 WROM 预警或库存预警，在 Web 端直接创建发货单 -> 调用 `shipOrder` -> 生成订单 (status=1)。
            2.  **收货**: 同上。
        *   **关键逻辑**: 
            *   **无限总库模式**: 商家端产品库 (`he_products`) 的库存默认视为“无限”，发货操作不因总库不足而阻塞，仅作记录用途。
            *   **药箱入库**: 客户点击“确认收货”时，增加客户个人库存 (`he_inventory.stock`)。
            *   **打卡消耗**: 每日任务完成时，系统自动扣减个人药箱 (`he_inventory`) 存量。
    
    *   **冷启动流程 (Cold Start)**:
        *   **场景**: 新用户首次登录，库存为 0。
        *   **动作**: 营养师在 Web 端建档配方时，直接发起 **Flow B**（首单发货）。
        *   **闭环**: 用户首次登录小程序 -> 首页弹窗提示“首单待收货” -> 点击确认 -> 库存初始化完成 -> 开启第一天打卡。

#### 3. 体感趋势 (Symptom Trend) [20%]
*   **定义**: 数字化体感的变化趋势。
*   **指标**: 心情 (Mood)、精力 (Energy)、睡眠 (Sleep)、肠道 (Digestion)。
*   **交互优化 (Simplified Input)**:
    *   保留 4 个维度，但统一使用 **3 个图标 (Emoji)** 进行选择。
    *   **映射值**: 
        *   😫 (差) -> 2 分
        *   😐 (还可以) -> 5 分
        *   😍 (很好) -> 8 分
    *   **客户端实现**: 
        *   **H5端**: 使用 SVG 平滑曲线展示趋势。
        *   **小程序端**: 自动降级为柱状图 (Bar Chart) 以避免崩溃。
*   **公式**: 
    *   计算本周平均分 $S_{curr}$ 与上周平均分 $S_{last}$。
    *   **进步奖励**: 若 $S_{curr} \ge S_{last}$，$Score = 15 + (S_{curr} - S_{last}) \times 5$ (最高 20 分)。
    *   **退步预警**: 若 $S_{curr} < S_{last}$，$Score = 15 - (S_{last} - S_{curr}) \times 10$ (最低 0 分)。

#### 4. 互动活跃 (Engagement) [10%]
*   **定义**: 健康行为参与度（非消息频次竞赛）。
*   **核心口径（v6.4）**:
    *   默认基础分为 8 分。
    *   统计近 7 天“活跃计划日”数量：当天任一行为成立即计入活跃日（有任务完成 / 有饮水记录 / 有体感记录）。
    *   互动分计算：`Score = clamp(7 + activePlanDays × 0.5, 7, 10)`。
    *   设计原则：不因“低聊天偏好”明显扣分，互动分只做轻量校准，不反向压制高依从客户。
*   **实时更新**:
    *   每次用户完成打卡 (`updateDailyPlanTasks`)，系统触发 `doCalculateWROM` 重新计算总分。
    *   **Web 端仪表盘**: 通过 `wrom_score` 字段实时获取最新高风险客户列表。
    *   **数据流闭环**: 打卡 -> 库存扣减 -> WROM 重算 -> 仪表盘更新。

#### 5. 数据采集埋点规范
| 功能模块 | 采集动作 | 对应 WROM 维度 | 数据要求 |
| :--- | :--- | :--- | :--- |
| 打卡 | 点击服用按钮 | 依从性、库存 | 必须记录 `timestamp` 与 `product_id` |
| 补货 | 点击确认收货 | 库存 | 必须更新 `he_inventory` 当前库存 |
| 体感 | 选择 Emoji | 体感 | 前端转换为 Int(2/5/8) 再入库 |
| 活跃行为 | 完成任务/饮水/体感任一记录 | 互动 | 必须能按天汇总 `activePlanDays` |
| 消息 | 查看通知/消息窗口 | 运营辅助 | 建议更新 `read_at`，不作为互动硬性扣分项 |

### 3.1.2 RPS 复购评分公式（v6.6）
*   **总分公式**: `RPS = 取消率(30) + 收货时延(25) + 复购周期(30) + 效果(15)`。
*   **取消率（30）**:
    *   数据来源: `he_orders.status`（已取消=-1）。
    *   计算: `cancelRate = cancelCount / totalOrderCount`，`Score = (1 - cancelRate) × 30`。
*   **收货时延（25）**:
    *   数据来源: `he_orders.shipped_at / received_at / updated_at`。
    *   计算: `receiptDelayDays = (received_at - shipped_at) / day` 的均值分段映射（2天内高分，超12天低分）。
*   **复购周期（30）**:
    *   数据来源: `he_orders.created_at`（仅已完成订单）。
    *   计算: 基于订单间隔均值、最近一次复购偏离比例、周期稳定性（CV）综合扣分。
*   **效果（15）**:
    *   数据来源: `he_daily_plans.symptoms[].value`（近30天）。
    *   计算: 基于体感评分均值与趋势变动（进步加分/退步扣分）。

### 3.1.3 业务预警逻辑 (Business Alert Logic)
*   **ΔRPS < 0 触发器**:
    *   当客户的 RPS 评分发生下滑（当前分数 < 上次分数）时，系统自动将客户的 `follow_up_status` 更新为 **“待回复”**。
    *   **目的**: 提醒营养顾问客户复购意愿可能在下降，需立即人工介入分析原因（如效果不佳、物流体验差等），严禁使用机械化自动回复。
*   **RPS < 60 触发器**:
    *   触发 **“复购风险预警”**，同样将状态更新为 **“待回复”**。
    *   计算: 比较近期体感均值与基线均值，叠加趋势增减与记录覆盖度得到最终分。

### 3.1.3 运营闭环 MVP（行动->执行->复核）
*   **目标**: 将“首要跟进行动”从提示文案升级为可执行、可追踪、可复盘的闭环。
*   **流程**:
    *   顾问在客户详情中点击“标记已执行”。
    *   系统记录行动快照（标题、建议、执行时 WROM/RPS 基线、复核到期时间=+3天）。
    *   3天后系统自动复核，重算双评分并回写变化值（`delta_wrom`、`delta_rps`）。
    *   若复核结果 `delta_rps < 0`，系统自动触发顾问预警通知，并将客户状态回写为“待回复”。
*   **数据表**: `he_followup_actions`。
    *   核心字段: `status(executed/reviewed)`, `baseline_wrom`, `baseline_rps`, `result_wrom`, `result_rps`, `delta_wrom`, `delta_rps`, `review_due_at`。

### 3.2 客户端页面逻辑 (Client UX - 90% Completed)
1.  **今日页面 (Home)**:
    *   **积分规则**: 完成一天 +1 分，连续 3 天 +1 分，连续 7 天 +2 分。
    *   **体感反馈**: 使用 3 个图标录入 4 个维度的体感值。
    *   **冷启动**: 无数据时展示友好引导页。
2.  **趋势页面 (Trends)**:
    *   **饮水曲线**: 独立图表展示，与体感/体重曲线分离。
    *   **健康指标**: 展示体重、体脂等生理指标趋势。
    *   **兼容性**: 针对小程序环境优化图表渲染逻辑。
3.  **库存页面 (Inventory)**:
    *   显示实际库存数量 (支持双单位显示，如 "2瓶 + 45粒")。
    *   显示在目前配方下的**预计覆盖天数**（需明确每日剂量）。
4.  **我的页面 (Profile)**:
    *   **我的配方**: 当前正在执行的配方。
    *   **月度总结 (Monthly Review)**: (原历史健康报告)
        *   **内容定义**: 不再是简单的 WROM 数据堆砌。
        *   **核心价值**: 营养顾问对客户上一个周期（如月度）的**定性点评**和**下阶段建议**。
        *   **形式**: 顾问在 Web 端编写的一段“给客户的话” + 关键成就徽章（如“全勤达人”、“睡眠改善显著”）。

### 3.3 异常流程与容错 (Exception Handling)
*   **取消订单**: 支持将 `status=0` 的订单取消，状态更为 `-1:已取消`。
*   **修改物流**: 支持营养师在 `status=1` 状态下修改物流单号和照片。
*   **幂等性检查 (Idempotency)**: 
    *   在“确认收货”逻辑中，必须先检查当前 `status` 是否严格等于 `1`。
    *   防止因网络波动导致重复增加库存。
*   **小程序白屏防护**:
    *   登录页与趋势页使用 `view`/`text` 替代 `div`/`span`。
    *   使用 Emoji 替代 SVG 图标。

### 3.4 消息触达机制 (Notification System)
*   **Flow A (客户下单)**: 触发给顾问的模板消息/弹窗提醒。
*   **Flow B (顾问发货)**: 触发给客户的服务通知。
*   **库存预警**: 当库存低于阈值时，除界面红点外，每日给顾问推送“低库存日报”。

## 4. 数据安全与多租户
*   **多租户隔离 (Multi-Tenancy)**: 
    *   **架构定义**: 系统原生支持多营养师入驻，每个营养师被视为一个独立的“租户”或“管理员”。
    *   **数据隔离 (Row Level Security)**: 
        *   在 PostgreSQL 中启用 RLS 策略。
        *   **营养师视角**: 只能查询到 `nutritionist_id` 等于当前登录用户 ID 的 `clients` 及其关联数据。严禁跨账户查看数据。
        *   **客户视角**: 只能查看属于自己的数据。
*   **身份认证 (Identity Anchoring)**: 
    *   **唯一标识**: 手机号 (Mobile Number) 是连接现实身份与数字身份的唯一桥梁。
    *   **登录安全**:
        *   **注册**: 强制设置登录密码。
        *   **登录**: 校验手机号与密码。
        *   **绑定机制**: 
            *   营养师在 Web 端创建档案时必填手机号。
            *   客户在小程序端首次登录时，点击“微信一键登录”授权获取手机号。
            *   后端自动匹配数据库中的手机号，若命中则自动绑定当前 OpenID，完成身份认领。

## 5. 核心 CRM 功能模块 (System Support Modules)
Web 端（系统支撑）模块采用了 CRM 化设计，确保 UI 一致性与操作效率。

*   **布局**: 仪表盘式布局，核心指标卡片置顶。

*    *   **双分布图**: WROM 健康风险分布 + RPS 复购风险分布。

### 5.3 营养学知识库 (Knowledge Base)
*   **布局**: 左侧/顶部导航 + 内容网格布局。
*   **功能**:

    *   **模态框编辑**: 支持快速添加和修改知识条目。

    *   固定四栏：今日、趋势、库存、我的。

    *   小程序端统一使用 `view/text`。
    *   趋势图复杂 SVG 在小程序端降级为柱状图。
*   **库存体验**:
    *   支持双单位展示（如“2瓶 + 45粒”）。
    *   与订单确认收货逻辑联动更新个人库存。

### 6.2 关键数据表约定
*   `he_users`: 用户基础信息（角色、手机号、streak）。
*   `he_daily_plans`: 每日任务快照。
*   `he_health_logs`: 体重、体感、饮水记录。
*   `he_inventory`: 用户库存明细。
*   `he_products`: 商品主数据（含 capacity、unit）。
*   `he_orders`: 补货订单与履约状态。
